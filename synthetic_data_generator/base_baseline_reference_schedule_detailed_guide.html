01 Â· Terminology

There are four different schedule concepts

Generator starting point

Base spread schedule

The schedule returned by _spread_schedule() before an occasion changes anything.

It is a deterministic template used to initialise both schedule copies.

Experimental comparator

Manual baseline schedule

The non-optimised plan stored in manual_baseline after the occasion overlay is applied.

This is the schedule used for comparison against the optimiser result.

Construction witness

Reference schedule

A hand-designed alternative stored in reference_schedule to verify that the intended scenario mechanism exists.

It is not an optimal solution and must not be supplied to the optimiser.

Research result

Optimiser schedule

The start days and modes selected by the MILP or Benders model.

This is the actual automated plan reported in the dissertation.

Important naming point: â€œbase scheduleâ€ and â€œmanual baseline scheduleâ€ are not always the same. The base spread schedule is the initial template. An occasion may deliberately modify that template to produce the manual baseline used in the experiment.
02 Â· Current mathematical-model alignment

The schedule data now supports F, P30 and P70

The current MATH4003 formulation defines three maintenance modes rather than one generic reduced-capacity mode. The updated generator uses the same retained-capacity fractions and exports the duration and loss values needed by the time-indexed model.

F

full_shutdown

0% capacity remains. This is the shortest maintenance duration.

P30

partial_30

30% capacity remains. Duration is longer than a full shutdown.

P70

partial_70

70% capacity remains. This is the longest maintenance duration.

duration(F) < duration(P30) < duration(P70), and capacity loss = 1 âˆ’ available capacity
The manual baseline still starts from full_shutdown. The optimiser is free to choose all supported modes, while the reference witness may use a partial mode only to verify that the mode-choice mechanism exists.

Why use different fractions?

The rule spreads task groups across different parts of their windows rather than placing every job at the earliest start.

It creates a simple, reproducible, non-optimised maintenance plan.

The fractions are benchmark-design assumptions, not evidence of an operational scheduling policy.

04 Â· Manual baseline

The schedule actually used for comparison

After the base spread schedule is created, the generator makes two copies: 

manual_baseline   = copy(base_spread_schedule)
reference_schedule = copy(base_spread_schedule)

The occasion function may then deliberately change selected decisions in the manual baseline. For example, a conflict scenario may move reclaimer and shiploader maintenance into a high-demand period.

Final definition: the manual baseline is the complete fixed maintenance plan that the automated optimiser must beat or improve upon under the same physical system, supply, demand, inventory, maintenance workload and task windows.

What is fixed in the baseline experiment?

Task start day: fixed to manual_baseline[j]["start_day"].
Maintenance mode: fixed to manual_baseline[j]["mode_id"].
Supply and demand: exactly the same as in the optimiser experiment.
Initial inventory: exactly the same as in the optimiser experiment.
Asset and network capacities: exactly the same as in the optimiser experiment.
Maintenance workload: the same mandatory tasks must still occur.

Baseline experiment

# Conceptual formulation
for each maintenance task j:
    start_day[j] = manual_baseline[j].start_day
    selected_mode[j] = manual_baseline[j].mode_id

# The flow model then finds the best operational response
# possible under this fixed maintenance plan.
The baseline is not simply the result of running evaluate_schedule(). The baseline is the fixed maintenance decision set. The final baseline outcome should be obtained by solving the same authoritative flow model used with the optimiser, with only the maintenance decisions fixed.
05 Â· X1 protected campaign overlay

How the special product changes the schedule logic

The base spread schedule is still created first. The X1 product definition and SpecialProductRequirements are part of every scenario, but only priority_campaign_conflict activates a strongly protected X1 campaign.

Manual baseline

Deliberate protected-route conflict

The occasion overlay moves M_TU3, M_ST4, M_RC3 and the active shiploader task into the X1 protected interval. This blocks the route TU3 -> ST4 -> Z4 -> RC3 -> SL2 in the default topology, or SL1 in the one-shiploader topology.

Reference witness

Same work, outside the interval

The reference witness retimes those same jobs so the X1 campaign, pre-buffer, post-buffer and cleanout are free of incompatible maintenance. It proves feasibility of the construction; it is not an optimiser solution.

Protected X1 interval

pre-campaign buffer + campaign window + post-campaign buffer

For the 90-day benchmark, the campaign loads on days 50-59. The protected maintenance-exclusion interval covers days 48-61. Cleanout uses one day before and one day after the campaign and is exported through the activity cleanout fields and sigma[a,d].

05 Â· Reference schedule

Why it exists and why it is not the research result

Purpose 1

Scenario verification

It shows that an avoidable conflict or recoverable feasibility problem was intentionally created.

Purpose 2

Test protection

Automated tests compare reference and baseline metrics to confirm the scenario still behaves as designed.

Purpose 3

Debugging aid

It helps identify whether a failed optimiser result comes from the solver or from a badly constructed instance.

The reference schedule is not: an optimal schedule, the expected solver answer, a warm start, a lower or upper bound, or the schedule used for the dissertationâ€™s final performance comparison.

Why it must remain hidden

If the optimiser is given the reference schedule, the research experiment becomes biased because the generator has already encoded knowledge of an improved arrangement. The optimiser should receive only the model data and, optionally, the manual baseline for the fixed-comparison run.

08 Â· Dissertation reporting

How to describe the schedules correctly

Recommended wording

A deterministic rule-based maintenance schedule was generated as the manual baseline. For each scenario, selected baseline decisions were modified to create the intended operating conflict. The integrated optimisation result was then compared with this fixed baseline under identical non-maintenance inputs.

Reference-schedule wording

A separate reference witness was constructed solely to verify scenario design. It was not treated as optimal, was not supplied to the optimiser, and was not used as the primary experimental comparator.

What not to claim

Do not say: the reference schedule is the optimal answer.
Do not say: the baseline is a real operator schedule unless it actually comes from operations.
Do not compare: optimiser results only against the lightweight evaluator if the authoritative model is different.
Do not change: demand, supply or initial inventory between the baseline and optimiser runs.
Final experimental comparison:
Manual baseline schedule versus MILP/Benders-generated schedule.

Reference schedule:
Generator validation and debugging only; it may demonstrate timing or F/P30/P70 mode flexibility.
